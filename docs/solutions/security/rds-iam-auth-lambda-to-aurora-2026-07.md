# RDS IAM auth from Lambda to Aurora (THINK-229 U1)

First landing of this pattern in the repo: `packages/lambda/analyst-reader-db.ts`
(the analyst broker's `analyst_reader` connection). What the next
Lambda-to-Aurora IAM migration should copy and what it should not rediscover.

## The shape

- **Token minting**: `@aws-sdk/rds-signer` `Signer.getAuthToken()` per
  (re)connect — hostname = cluster endpoint DNS, exact-case DB username,
  region. Tokens are 15-minute, **connect-only, and reusable**: an
  established connection outlives its token by design, so the cached
  `pg.Client` pattern keeps working; re-mint only on reconnect.
- **The runtime does NOT bundle `@aws-sdk/rds-signer` reliably** — add the
  handler to `BUNDLED_AGENTCORE_ESBUILD_FLAGS` in `scripts/build-lambdas.sh`
  so the pinned package inlines (default flags externalize all `@aws-sdk/*`).
- **IAM policy**: `rds-db:connect` on
  `arn:aws:rds-db:<region>:<acct>:dbuser:<CLUSTER-RESOURCE-ID>/<role>` — the
  immutable resource ID (`cluster-XXXX`), **never** the cluster ARN.
  `aws:SourceIp`/`aws:SourceVpc` conditions are unsupported on this action.
- **TLS**: IAM auth requires SSL. The Lambda Node runtime does not trust the
  RDS CA, so THINK-228 had shipped `sslmode=no-verify`. The fix is an
  **embedded** copy of the RDS global trust bundle
  (`packages/lambda/rds-ca-bundle.ts`, regenerated by
  `scripts/update-rds-ca-bundle.sh`) with `ssl: {ca, rejectUnauthorized: true}`
  — no filesystem asset copy needed in the esbuild single-file bundle.
- **Retry**: one fresh-token retry absorbs under-load transients. This paid
  off in the FIRST live connect: attempt 1 hit a 5s connect timeout, the
  fresh-token retry carried. Always set `connectionTimeoutMillis` so a hung
  connect fails into the retry instead of eating the invocation.

## Cutover choreography (the part that bites)

`GRANT rds_iam TO <role>` **disables password login for that role the moment
it applies**. Ordering that avoids any outage window (KTD2 dual-path):

1. Ship IAM-first-with-password-fallback code + terraform (cluster flag,
   `rds-db:connect`, env). Gate the fallback on **auth-shaped errors only**
   (28000/28P01/PAM) — a transport failure must rethrow, or an on-path
   attacker can force the credential downgrade.
2. `iam_database_authentication_enabled = true` needs
   **`apply_immediately = true`** on `aws_rds_cluster` — the provider default
   defers cluster modifications to the maintenance window, and a GRANT landing
   inside that pending window strands BOTH auth paths. Pre-apply gate:
   `describe-db-clusters` must show the flag true with no
   `PendingModifiedValues`.
3. THEN apply the GRANT migration to dev via psql; verify a live
   `strategy:"iam"` connect log; THEN merge the migration file (drift-gate
   marker: `-- creates-role-membership: rds_iam:<role>`, a probe type added
   for this).
4. Rollback pair: `REVOKE rds_iam FROM <role>` restores password login and
   the fallback picks it up on the next reconnect. Keep the password secret
   alive as that rollback pair until the IAM path has soaked; retire it as a
   dated follow-up.

## Audit reality

CloudTrail does **not** log IAM database authentication
(`generate-db-auth-token` is client-side SigV4 — it never calls an AWS API).
Credential-use audit = the caller's structured connect/query logs (which can
carry verified caller identity — better attribution than a connect event)
plus Postgres `log_connections` exported to CloudWatch.

## Related gotchas from the same arc

- A role migration that asserts zero role memberships (`pg_auth_members`)
  will trip on the deliberate `rds_iam` membership — allowlist it explicitly
  (drizzle/0227 vs 0229).
- Reconciler probes over a granted-table manifest must mirror the grant
  migration's `to_regclass` tolerance: `has_table_privilege` THROWS on
  nonexistent relations, and dev drifts from the Drizzle schema — an absent
  table is not a grant breach (PR #3544).
- Grouped IAM managed policies cap at 6,144 rendered chars; check headroom
  before adding statements (`api-data-plane` was at 6,018 when a ~200-char
  DLQ grant broke deploys — PR #3542 rebalanced).
