Mobile Inline Analytics Charts

Date: 2026-08-07  ·  Topic: mobile-inline-analytics-charts  ·  Mode: repo-grounded
Focus: Land brain analytics responses in the Mobile app with rich in-thread chart UX — reuse the Plate SVG chart technology to render charts inline in the conversation thread instead of emitting an artifact. Target UX per user mockup: inline chart card (title, funnel, caption takeaway) with a collapsible "Chart data" table beneath it.

Grounding Context

Codebase context. The "Plate SVG technology" is the Document Compositor's house chart renderer (packages/api/src/lib/artifacts/document-charts.ts): pure, deterministic string-template functions from ChartDirectiveData to static SVG — no script, no DOM, hardcoded 720×250 viewBox, XML-escaped at the boundary, colored exclusively through CSS custom properties (var(--accent), var(--ink)…). It renders tw:chart fenced directives (kinds: bar, line, donut, stat-strip, sparkline, meter, funnel) compiled server-side into scriptless plate HTML, viewed on mobile through a JS-disabled WebView behind a link-out card. Separately, web thread GenUI renders Recharts charts from a disjoint catalog (area|bar|line|pie, packages/thread-json-render/src/catalog.ts:302); mobile's GenUI registry has no chart entry, so charts degrade to an "Open this thread on web" card. react-native-svg@15.12.1 is already a mobile dependency, unused for charts. Analytics transport today: agent markdown with tw:* directives, typed Message.parts (Vercel AI SDK shape), and data_view artifact rows that render identically to generic report cards.

Verified corrections. Two claims were adversarially checked and settled this run: (1) react-native-svg cannot resolve CSS custom properties — house SVG strings handed to SvgXml unmodified render unstyled; every native-SVG idea below requires a literal-color substitution pass. (2) The analytics-display portable contract (AnalyticsDisplayRenderPayload, THNK-57) never shipped — no such package exists in the repo; the learnings doc claiming it did (analytics-display-portable-contract….md) is stale.

External context. The dominant 2026 generative-UI pattern is "agent emits a validated declarative spec from a pre-approved catalog; each client renders natively" (Vercel AI SDK, Google A2UI, VegaChat, chat2plot) — validating the chart-as-data direction over server-rendered pixels. Mobile engine tiers: react-native-svg (light, static), Skia/Victory Native XL (GPU, +3–5 MB), WebView-in-thread (unendorsed; scroll jank in FlatList). ChatGPT ships an inline static/interactive chart toggle.

Known pain. Adding a tw: directive kind touches ~7 hand-maintained seams that fail silently (THINK-205 shipped a defect caught only by pixel-level dogfooding). Web's --chart-1..5 tokens are byte-identical in light and dark (dark mode is a no-op); mobile's one SVG feature (TurnExecutionTimeline) hardcodes hex and ignores its own isDark prop.

1

Chart-as-data: ChartDirectiveData becomes a typed message part

analytics-payload-contract Confidence 85% Complexity Medium
Description
Break the assumption that the compiler's output (HTML/SVG) is the transport. The server keeps validating tw:chart fences, but emits the already-closed ChartDirectiveData shape (type, title, qualifier?, series[1–24], caption?, max?) as a typed part on the message — alongside, not instead of, document compilation. Each client renders the data with its own engine; the server stays the single validator. Mobile gets its chart with the turn, in the scroll, with no artifact fetch and no navigation.
Basis
direct: packages/api/src/lib/artifacts/document-directives.ts:292-305 — ChartDirectiveData is a closed, serializable interface and rendering is already injected (export type ChartRenderer = (data: ChartDirectiveData) => string); packages/database-pg/graphql/types/messages.graphql:33-40 — typed UIMessage parts are persisted at turn-finalize. external: spec-as-data is the converging industry pattern (VegaChat, chat2plot, Google A2UI).
Rationale
The whole cross-surface problem dissolves if the wire format is the directive's data, not its render. The persistence slot already exists — no new tables, no new artifact type — and the deferred THNK-34 inline-analytics plan already specified exactly this portable-payload shape before it stalled. The mobile mockup is the forcing function to un-defer it.
Downsides
Touches the GraphQL schema and turn-finalize path, so it needs cross-team sign-off before either client builds against it. Duplicates chart data between the compiled document and the message part for document-shaped responses.
2

Run the house renderer on-device, with a resolved chart-role token contract

chart-rendering-engine Confidence 75% Complexity Medium
Description
Extract the house chart renderer into a shared package and run it on the phone: mobile calls renderChart(data, frame, palette) locally and mounts the SVG string via react-native-svg's SvgXml. Two changes make it portable: (a) parameterize the hardcoded 720×250 frame so layout reflows at actual device width and font scale (the funnel's 10px tick labels are illegible when a desktop SVG is scaled to a 360pt card); (b) replace var(--x) color references with a resolved palette parameter — a shared chart-role token contract (ink, muted, accent, line, series ramp) resolved to literal colors per surface and theme. Web CSS consumes the same roles via cascade; mobile passes literal values; email inlines safe hex.
Basis
direct: document-charts.ts:1-20 — "pure, deterministic functions from directive data to static SVG… no script, no external references, fixed viewBox layout arithmetic, no randomness" — nothing depends on a server or DOM. direct: verified this run: react-native-svg cannot resolve CSS custom properties, so palette resolution is mandatory, not optional. direct: packages/ui/src/theme.css:74-78 vs 109-113 — --chart-1..5 byte-identical in light and dark; TurnExecutionTimeline.tsx hardcodes hex and never uses its isDark prop for strokes.
Rationale
This is the user's "Plate SVG technology on mobile" instinct, sharpened: share the renderer function, not the SVG string. Mobile gets all 7 house kinds — including the mockup's funnel — with zero WebViews in the thread, and the token contract fixes two shipped theming defects (web's dark-mode no-op, the timeline's ignored isDark) as side effects rather than new work.
Downsides
The extraction moves audited rendering code across a package boundary (the KTD4 inject-after-sanitize gate must be preserved on web). Reflow means mobile output diverges pixel-wise from the server render — golden-render CI (idea 6) becomes more important. Dynamic Type support requires the layout functions to accept font scale, a real but mechanical parameterization.

Ship the mockup card: inline chart + caption + collapsible "Chart data" table

thread-inline-ux Confidence 90% Complexity Low
Description
Build the inline analytics card exactly as mocked: title, chart, caption takeaway ("Numo ($50k) is the highest-value deal in Negotiation"), then a collapsible "▶ Chart data" disclosure revealing the table — rendered directly in the thread scroll. Concretely: give data_view its own card body instead of the generic report treatment, register a chart component in the mobile GenUI registry so the "Open this thread on web" fallback stops firing for charts, and derive the disclosure table from the chart's own series array rather than having the agent author the numbers twice.
Basis
direct: apps/mobile/components/chat/ArtifactCard.tsx:15-22 — data_view is mapped to the same config as report ("no special inline rendering"); apps/mobile/lib/genui-registry.ts:146-154 — the registry holds only task_list, task, question_card, and everything else degrades to the open-on-web card; app/settings/usage.tsx:120-125 — the collapse/chevron pattern already ships in the app.
Rationale
This is the deliverable the user pointed at and called perfect. Every piece of chrome it needs already exists (card, badge, disclosure); only the chart body is new, so it is the highest-certainty, lowest-novelty-risk item on the list — and deriving the table from series kills a data-drift risk inside a single message before it is born.
Downsides
Depends on a chart body renderer existing (ideas 2 or 5 supply one). Card-level scope only — multi-chart responses and interactivity are deliberately deferred.
4

The Trustworthy Chart Block: fallback, narration, and provenance as required fields

analytics-payload-contract Confidence 80% Complexity Medium
Description
Define the analytics unit the way Slack Block Kit defines rich blocks: a chart block is invalid unless it carries all its representations — {chart data, takeaway caption, table rows, one-sentence summary} — validated at emission like tw:sources already is. Three payoffs from one validation layer: (a) degraded clients render table-first instead of an apology card, making "Open on web" structurally impossible; (b) screen-reader narration is derived from the data by one shared function ("Funnel, six stages, Contacted 2 down to Won 3; takeaway: …") instead of per-surface ARIA; (c) the existing provenance ledger cross-check extends to gate chart numbers — a chart whose figures don't trace to a tool call this turn is rejected for self-repair, the same way citing an uncalled tool already is.
Basis
direct: packages/pi-extensions/src/document-composer.ts:135-181 — the ledger cross-check already rejects tw:sources fences citing uninvoked tools and returns a REJECTED result for self-repair; packages/api/src/lib/artifact-delivery.ts:59-67 — "raw YAML must never reach a recipient" is already email's contract; document-directives.ts:299 — caption is contractually "the takeaway, not a chart description." external: Slack Block Kit's mandatory per-block text fallback is why Slack never shows a broken block.
Rationale
Reframes "how do we render charts on mobile" into "what must an analytics block always carry" — and the answer makes the mockup's chart+caption+disclosure-table the contract's natural rendering, with accessibility and degraded surfaces solved by the same required fields. The provenance leg matters most: an inline chart is exactly where a hallucinated pipeline number is most damaging and least detectable in front of a customer.
Downsides
Stricter emission validation means more agent self-repair round-trips; the narration function and number-tracing heuristics need real design work (aggregates vs raw tool rows).

Render ladder: PNG sidecars v0 → native SVG v1 → tap-to-open inspector v2

chart-rendering-engine Confidence 75% Complexity Medium, staged
Description
Sequence the engine work as a ladder off one payload. v0: at compile time the server rasterizes each chart into light- and dark-theme PNG sidecars; mobile renders a plain <Image> — zero parse cost, perfectly scroll-safe, ships the mockup next sprint, and structurally sidesteps the var() problem (colors baked server-side). It also upgrades email from table-only to image charts for free. v1: swap the body for the shared on-device renderer (idea 2) to gain sharpness, Dynamic Type, and offline generation. v2: tap opens a full-screen GPU inspector (Victory Native XL / Skia: scrub tooltips, drill-in) fed by the same ChartDirectiveData — ChatGPT's shipped static/interactive toggle, adapted to a FlatList thread where the toggle is navigation.
Basis
direct: artifact-delivery.ts:59-67 — email's table-only degradation exists because clients strip SVG; PNG sidecars repair it. external: ChatGPT's interactive/static chart toggle; Victory Native XL / react-native-skia documented at 60–120fps for +3–5 MB binary; resvg/sharp are proven Lambda rasterizers. reasoned: each rung delivers user-visible value alone and no rung blocks the next — the payload contract is the only shared dependency.
Rationale
The fleet's engine candidates (bake variants, reflow on-device, render endpoint, GPU) are usually framed as competitors; sequencing them as a ladder converts an architecture fight into a shipping plan. v0 is the only path that gets the mockup in front of users while the renderer extraction (idea 2) is still in flight.
Downsides
PNGs are blurry on zoom and ignore Dynamic Type (acceptable for a v0, which is why v1 exists); the v2 inspector's +3–5 MB binary cost needs an explicit product yes/no; three rungs means the team must resist stopping at v0 forever.
6

Drift insurance: crown the house catalog, codegen the seams, golden-render CI

cross-surface-parity Confidence 70% Complexity Medium
Description
Before mobile becomes a third chart surface, retire the conditions that make surfaces drift. (a) Crown the house catalog (bar|line|donut|stat-strip|sparkline|meter|funnel) as the single analytics chart vocabulary — the GenUI catalog (area|bar|line|pie) cannot even render the mockup's funnel, and the competing analytics-display/v1 contract was confirmed never-shipped, so this is a decision, not a migration. (b) Codegen the mirrors: generate web's PLATE_DIRECTIVE_KINDS, exemplar snippets, workspace-defaults guidance, and the new mobile registry from DEFAULT_REGISTRY at build time, so mobile never becomes hand-synced seam #8. (c) Golden-render CI: one fixture corpus (every kind × edge cases × themes) rendered by every engine, snapshot-diffed — byte-exact, because the renderer was engineered deterministic (r2() exists precisely to kill float noise).
Basis
direct: docs/solutions/architecture-patterns/new-tw-directive-kind-checklist.md — 7 hand-maintained seams, "silent UX gap if missed, not test failure," THINK-205 shipped and was caught only by pixel-level dogfooding; document-charts.ts:38-39 — "Fixed-precision coordinate — kills float noise, keeps output stable"; verified this run: no analytics-display package exists anywhere in the repo.
Rationale
Every engine idea above adds a renderer or a variant, which multiplies exactly the drift surface the repo's own history flags as its chronic failure mode. This bundle is the prerequisite that makes having more than one render target safe — and determinism already paid for the CI leg; nobody is collecting the payoff.
Downsides
Contradicts the (unshipped) portable-contract plan's catalog, so the team must formally supersede it; codegen infra is unglamorous work that competes with the visible mockup for priority; cross-engine snapshots need per-engine harnesses.
7

Takeaway-first: the insight is the unit, the chart is the garnish

thread-inline-ux Confidence 65% Complexity Low
Description
Design the mobile analytics unit insight-first: takeaway sentence leads, then a stat-strip or chart when the kind survives a phone width, table always available under disclosure. Encode per-kind mobile fitness rules — a 24-point donut on a 360pt screen should choose to render as a stat-strip + table instead of an unreadable chart. Small-screen degradation becomes a design principle rather than a failure mode.
Basis
direct: document-directives.ts:299 — the contract already encodes the hierarchy: caption is "the takeaway, not a chart description." The user's own mockup foregrounds the annotation line. reasoned: the analytics answer's value is the judgment ("Numo is the highest-value deal in Negotiation"), which survives every screen size; the chart is evidence for it, and evidence can change form.
Rationale
Cheap insurance against the most likely quality failure of this whole program: shipping technically-correct charts that are illegible or meaningless at phone width. Forces the per-kind fitness conversation before renderer code hardcodes assumptions.
Downsides
Fitness rules are judgment calls that need design ownership; risks over-suppressing charts users actually want if tuned conservatively.
