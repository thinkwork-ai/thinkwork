Controlled-Loop Simplification

Date 2026-07-16 Topic controlled-loop-simplification Focus Incorporate the Emerging AI "agent as a controlled loop" model (Trigger → Goal → Tools → State → Check → Stop) to simplify ThinkWork's loop strategy Mode repo-grounded

ThinkWork's loop machinery has grown into parallel subsystems that each own a slice of the article's six-piece loop. The strongest, verified finding of this session: the Check slot is empty in production — decideWorkflowContinuation stamps exit_signal_satisfied whenever the model calls goal_complete; the declared exitSignal text is never evaluated, and completionCriteria are prose folded into the prompt. Every ranked idea below deletes or consolidates something; none adds a parallel mechanism.

Grounding Context

Codebase Context. Loop execution spans: three Pi invoke payload builders (chat-agent-invoke, wakeup-processor, buildAgentLoopWakeupPayload/interpreter-wakeup) kept in parity by a solutions doc and a test — three production bugs to date; goal completion signaled exclusively by the model calling goal_complete (judge modes declared in contracts.ts but removed from the product surface in THINK-137 U10); three run ledgers (workflow_runs, agent_loop_runs/agent_loop_iterations, thread_turns) tracking the same execution; context_snapshot rebuilt from the wakeup payload every turn with no run-level STATE store; stop conditions split across two inconsistent enforcement surfaces (legacy completion-decision.ts checks maxTokens/maxRuntimeMs; the canonical interpreter checks only maxIterations; costBudgetUsd enforced nowhere); the stall monitor disabled 2026-07-15 for false timeouts (THINK-301); no-progress detection absent. Working ratchets already exist — skill-eval-gate (staged scoring, deferred swap) and the hermetic fixture gate on routine proposals (which correctly blocked a bad fixture on the first live autonomous admission, 2026-07-15).

External context. The 2025–26 ecosystem converged on exactly the article's primitives: Claude Code /goal (separate cheap evaluator grades an objective condition per turn), Ralph loops (fresh session per iteration; state in files, "agents forget, repositories do not"), llm-stop-conditions (named composable stops, every stop returns a reason), OpenAI Agents SDK (approval = paused run, budgets consistent across gates), Kubernetes reconciliation (level-triggered re-derivation from declared state). Market gap: no multi-tenant enterprise harness packages per-tenant checklisted goals + auditable stop reasons + approval-as-paused-run — a governance story ThinkWork is positioned to own.

1

Make the Check real — external per-turn grading of completion criteria

goal-completionConfidence 90%Complexity Medium
Description
Today a loop "completes" when the model calls goal_complete — a self-certification prompted by an instruction, with completionCriteria string-joined into the objective and the declared exitSignal never evaluated by any code path. Give the Check slot a real occupant: at save time, criteria must resolve to a gradeable check (command exit code, data query with expected shape, eval case, or LLM rubric — ungradeable goals are rejected at authoring); after each turn, a cheap evaluator model grades the declared criteria against the turn's evidence and returns PASS or a numbered failure list; the loop exits only on PASS. goal_complete becomes "request grading," not "declare victory." This is deliberately not a resurrection of the six judge modes THINK-137 deleted — it is one check path, and it deletes surface: the decorative exitSignal field, prose-only criteria, and the dead judge-mode scaffolding still declared in contracts.ts:27-39.
Basis
direct: Verified in packages/agent-loops-core/src/interpreter.ts — decideWorkflowContinuation branches only on goal-run status and never inspects policy.exitSignal; loop-to-workflow.ts:90-93 — exitSignal = completionCriteria.join("; ") || objective.trim(); completion-decision.ts — "This is NOT a judge — the worker's own goal-run signal drives completion… there is no judge verdict anymore." external: Claude Code /goal — separate cheap evaluator (Haiku-class) grades the condition per turn and returns a reason string.
Rationale
The self-extension arc proved the behavioral law: "fabrication is the failure mode when posture is closed but the loop is absent." An agent under iteration pressure will call goal_complete optimistically — the article treats an external check as the non-negotiable piece of a working loop, and it is precisely the piece ThinkWork's loops lack. This also unlocks ideas 5 and 6: the check output is the substrate for evaluator fixtures and no-progress detection.
Downsides
Narrowly re-opens a decided deletion (THINK-137 U10) — needs explicit re-adjudication that "one check path" is not "six judge modes back." Adds a per-turn evaluator invocation (cheap model, but nonzero cost/latency). Migration story needed for existing loops with vibes-criteria.
2

Pointer payloads + a run STATE document

loop-stateConfidence 80%Complexity High
Description
Attack the payload-parity bug class at its cause. Today three builders each snapshot every capability-gating field into the wakeup payload, and context_snapshot is rebuilt from that payload every turn — so every new field must be added to all builders and "carried identically on the initial ('start') and resume payloads." Flip to level-triggered dispatch: the wakeup carries {runId, iteration, reason, provenance} and the runtime re-derives goal, document binding, gates, and identity from declared state at turn start. Pair it with the article's most concrete prescription: each run carries one small STATE document (Goal / Completed / Evidence / Next action / Blockers) written at finalize and read at dispatch; full history stays in the turn ledger and is never reloaded. A shared-payload-builder extraction is the weaker fallback if the full inversion is too large a bite.
Basis
direct: Parity doc docs/solutions/architecture-patterns/wakeup-processor-payload-parity-with-chat-agent-invoke-2026-06-12.md — "Anything the runtime gates on payload fields must be added to both, or the capability silently exists only on direct chat turns. This has now bitten three times"; run-ledger.ts:462-463 (verified verbatim) — "Carried IDENTICALLY on the initial ('start') and resume payloads"; evidence dossier — "context_snapshot: RELOADED each turn from wakeup payload… No RUN_LOG or STATE files found." external: Kubernetes level-triggered reconciliation; Ralph loops' files-over-history.
Rationale
Three production incidents share one root cause, and the org's own postmortem prescribes the refactor. But extraction still leaves an edge-triggered design where documentation enforces correctness; pointer payloads make the failure class structurally impossible and shrink the Pi dispatch contract to "given a runId, reconstruct the turn." The STATE document gives loops durable, model-legible progress — the one thing the wakeup payload can never carry.
Downsides
The largest blast radius on the list: touches chat dispatch latency, the Pi runtime contract, and resume semantics. Needs staged migration (loop/wakeup paths first, chat last). Fresh-context iterations (the Ralph variant) are worth piloting on one loop family, not mandating platform-wide.
3

One trigger vocabulary

triggers-wakeupsConfidence 85%Complexity Medium
Description
Verification found the fragmentation is worse than the dossiers reported: at least four trigger vocabularies coexist — nine trigger_type values on scheduled_jobs, a six-value AgentLoopDispatchTriggerFamily union, JobTriggerEvent.triggerType with 10+ values plus bolted-on webhook fields, an eight-value APPROVAL_TRIGGER_FAMILIES, and loose ad-hoc strings (eval_scheduled, skill_run, canvas_refresh) compared via raw startsWith("agent_") checks. Collapse to one Trigger contract: a single startRun(loopId, provenance, payloadPointer?) entry point where schedule/webhook/manual/event/approval-resolution are thin adapters supplying provenance as data, never behavior. The webhook provenance seam (fenced untrusted payload) becomes the one payload mechanism for every family.
Basis
direct: scheduled-jobs.ts:47 (9 values, verified), run-ledger.ts:45-51 (6-family union, verified), job-trigger.ts (overlapping unions + APPROVAL_TRIGGER_FAMILIES + ad-hoc constants, verified by fresh-context reviewer). reasoned: the article needs exactly one thing from a trigger — a reason to start the loop; everything else is attribution.
Rationale
Every new trigger source today means touching job-trigger, run-ledger, and the payload builders in lockstep. If post-dispatch behavior never actually branches by family (the forcing question for the room), the whole surface collapses to a log field, and testing one function tests every family.
Downsides
Schema migration on scheduled_jobs.trigger_type plus a compatibility window; approval-resume semantics (budgets carry forward, not reset) need explicit design so the gate doesn't silently reset counters.
4

Unified stop policy — one composed evaluator, named reasons, enforce-or-delete

stop-budgetsConfidence 80%Complexity Medium
Description
Verification corrected the raw finding: it is not "budgets declared, enforced nowhere" but two parallel enforcement surfaces with inconsistent coverage — the legacy AgentLoop path (completion-decision.ts) checks maxTokens and maxRuntimeMs, while the canonical interpreter's ContinuationPolicy carries only exitSignal/maxIterations/oversight; costBudgetUsd is enforced nowhere; the approval-step timeout appears unenforced. Consolidate onto one evaluateStops(state, policy) → {stop, reason} function — composed named conditions (MaxIterations, MaxUsd, MaxSeconds, NoProgress, LeaseExpired, ApprovalTimeout) — invoked at the single continuation seam. Every field in the contract is either enforced there or deleted; every stop writes its named reason to the run. Fold in the two near-identical budget-pause blocks in cost-recording.ts as one scope-parameterized autonomy-freeze primitive (SRE-style: exhaustion freezes autonomy and requires approval, richer than a kill switch).
Basis
direct: contracts.ts:97-99 (fields declared) vs workflow-definition.ts:403-416 (ContinuationPolicy carries only exitSignal/maxIterations/oversight) vs completion-decision.ts budgetStopReason (checks maxTokens/maxRuntimeMs on the legacy path) — all verified; cost-recording.ts:340-429 duplicate blocks verified. external: llm-stop-conditions — composable named stops, every stop returns should_stop + a reason.
Rationale
An operator who sets costBudgetUsd today gets nothing — a declared-but-inert safety knob in a multi-tenant enterprise product. Auditable named stop reasons are also the differentiator the external research flags as unpackaged by any SDK. One seam, one composition, honest contract.
Downsides
Per-run cost attribution (for MaxUsd) needs a cost rollup keyed to the run, which today requires joining cost_events; deciding enforce-vs-delete per field is a product call that will break some existing configs.
5

One verification gate contract — loops ride the existing ratchet

verification-ratchetConfidence 75%Complexity Medium
Description
ThinkWork already shipped the article's ratchet — twice: skill-eval-gate (candidate scored against a staged dataset; workspace swap deferred below threshold) and the hermetic fixture gate on routine proposals ({status: green|red, fixtures:[…]}; promotion only on green — and it correctly blocked a bad fixture on the first live autonomous admission). Loops are not customers of either: loop version edits swap live with zero scoring, and no run-level snapshot records which version executed. Unify the verdict/evidence contract (the neutral verdict.source seam in evals-core exists for this) and make loop-version promotion a gate client: each loop carries a small benchmark; a new version installs only when it meets the incumbent's pass rate. Apply "evaluate the evaluator" to idea 1's checks — a completion check may not gate anything until it passes known-pass and known-fail fixtures.
Basis
direct: skill-eval-gate.ts:2-11 (verified verbatim) — "workspace swap DEFERRED… HELD until an operator applies it"; routine-proposal.ts:~412-438 hermetic-green promotion (verified); evidence dossier — "Agent loop version snapshot NOT stored per run." external: evaluator-hardening practice (known-pass/known-fail fixtures before trusting a judge as a gate).
Rationale
"The evaluation is the ratchet — without it the agent is not improving, it is only moving." Consolidating three bespoke gates into one contract is pure simplification, and it closes THNK-46's core unresolved gap (no one contract tying goal, judgment, and evidence together) with machinery that is already live and proven.
Downsides
Loop benchmarks need authoring (the article's "20 real cases" discipline) — cheap per loop but nonzero operator effort; gate friction on loop edits must have an operator override, mirroring skill-eval-gate's.
6

Progress-based liveness — replace the disabled stall monitor

stop-budgetsConfidence 70%Complexity Medium
Description
The stall monitor infers liveness from an activity timestamp that nothing is obligated to feed — chat turns never bump last_activity_at, so it produced false timed_out verdicts and was disabled in production (THINK-301). Replace inference with proof, in either or both of two shapes: (a) a finalize-renewed lease — every dispatch writes lease_expires_at; the only renewal event is finalize; expiry is terminal, checked by a trivial sweep; a waiting_for_human run holds a longer lease, giving approval gates their timeout for free; (b) check-output diffing — two consecutive identical failure lists from idea 1's grader is itself the no_progress stop, with the numbered failures as the blocker report. A Fischer-increment extension (progress earns iterations; unproductive turns drain the bank) can replace the flat maxIterations cap later — worthwhile only framed as a replacement, not an addition.
Basis
direct: stall-monitor.ts:1-75 (verified) — STALL_THRESHOLD_MINUTES = 5, COALESCE(last_activity_at, started_at); memory/THINK-301 — disabled 2026-07-15; evidence dossier — "No-Progress Detection: ABSENT." external: Chubby/etcd leases (liveness proven by renewal, never inferred); Kubernetes requeue-with-backoff.
Rationale
THINK-301 is at Requirements Review right now — this is a competing requirement that deletes the failure-prone mechanism instead of patching every code path to remember to bump a timestamp. "Is it getting closer?" is the right question; "is it moving?" already failed in production.
Downsides
Check-output diffing depends on idea 1 landing first; the lease design must pick renewal points carefully (finalize-only is clean but long tool-running turns need a lease horizon longer than the longest legitimate turn).
7

One run ledger — thread_turns as journal, the rest as projections

loop-stateConfidence 65%Complexity High
Description
Three ledgers record the same execution at different grains, joined ad hoc (agent_loop_iterations.thread_turn_id). Adopt the accounting split: thread_turns — where finalize idempotency, cost, and usage already land — is the only independently written journal; agent_loop_runs/agent_loop_iterations and the run-level rollups on workflow_runs become finalize-time projections, with a cheap trial-balance check (projected totals must match journal totals) instead of three write paths that can disagree. Pin a loop-version snapshot per run at dispatch, copying the eval profile_snapshot pattern, so a mid-flight definition edit never reinterprets a running loop.
Basis
direct: evidence dossier — "Three separate ledgers tracking the same execution from different perspectives… No direct run-level state store"; evaluations.ts:254-255 (verified) — profile_snapshot pinned at dispatch. external: double-entry journal/subledger separation with mechanical reconciliation. Aligns with the parked canonical-run-model plan (2026-07-07, "single ledger").
Rationale
Gives the canonical-run-model plan its hardest missing decision (which table is the source of truth) and a migration shape that deletes write paths incrementally rather than big-bang merging tables. Every future loop feature stops asking "which ledger do I write?"
Downsides
Verification flagged this as a heavier lift than the raw idea admits — the three ledgers sit at genuinely different grains (run/iteration/turn), so "become projections" is a multi-PR migration, not a refactor. Sequence after ideas 2–4 shrink what the ledgers must carry.
Sequencing note

Idea 1 is the keystone: its check output feeds idea 6's no-progress detection and is governed by idea 5's fixture gate. Ideas 2–4 are independent consolidations that can start in parallel. Idea 7 gets cheaper after the others shrink the state the ledgers carry.
