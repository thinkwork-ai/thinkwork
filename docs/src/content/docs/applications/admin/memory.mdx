The Memory page is the operator view for retained Bedrock AgentCore Memory records. It reports what AgentCore extracted from completed turns, shows the namespace and facet each record landed in, and lets operators correct or delete a record.

**Route:** `/settings/memory`
**Route wrapper:** `apps/web/src/routes/_authed/settings.memory.tsx`
**Page implementation:** `apps/web/src/components/settings/SettingsMemory.tsx`

## Layout

The page has three primary controls:

- **Facet filter** — narrow to semantic, preferences, summaries, or episodes.
- **Search bar** — text search across operator-visible memory records, backed by `memoryRecords(scope: OPERATOR)` and `memorySearch`.
- **Refresh** — manual re-fetch of records, episodic records, and retain diagnostics together.

Below the controls, the page renders a `DataTable` of memory records.

## Memory Records

The table view shows:

| Column    | Notes                                                          |
| --------- | -------------------------------------------------------------- |
| Date      | When the record was created                                    |
| Facet     | Strategy badge: semantic, preference, summary, episode         |
| Namespace | The AgentCore memory namespace the record was extracted into   |
| Memory    | Truncated content preview                                      |
| Score     | Relevance score, present on search results                     |

Clicking a row opens a detail sheet with the full content and record metadata. Records can be edited or deleted one at a time.

Two reads back the table: `memoryRecords` for durable extracted memory and `memoryEpisodicRecords` for session-scoped episodes. They are separate queries because AgentCore stores them in different namespaces.

## How records get here

Nothing on this page writes memory. The Pi runtime calls the `memory-retain` Lambda once per completed turn, the Lambda calls `retainTurn`, and AgentCore runs its own background extraction into the semantic, preferences, summaries, and episodes namespaces. Extraction is asynchronous, so a turn can be `retained` a moment before its record is searchable here.

<Aside type="note">
  A retained turn does not guarantee a record. AgentCore decides what is worth
  extracting; a turn that asked a question rather than stating a fact often
  produces nothing. Check `memoryRetainAttempts` before concluding the pipeline
  is broken — the repo's `docs/runbooks/memory-retain-recall.md` walks the
  triage path.
</Aside>

## Workflows

### Audit What an Agent Remembers

1. Open `/settings/memory`.
2. Search for a term, or filter by facet.
3. Click a row to read the full content and record metadata.
4. Use the namespace and facet to verify which extraction path produced it.

### Debug Memory Results

1. Reproduce the agent's `recall` call or the explicit `query_memory_context` call.
2. If a memory hit looks wrong, open `/settings/memory`.
3. Search for the same term.
4. Inspect the raw record and its retain attempt.

### Delete or Correct Sensitive Memory

1. Search for the sensitive term.
2. Click into each matching record.
3. Edit the content in place, or delete the record outright.

Mutations are one record at a time; there is no bulk edit or bulk delete.

## Data Model

- **Semantic** — durable extracted facts.
- **Preferences** — how the requester wants the agent to work.
- **Summaries** — condensed rollups of prior work.
- **Episodes** — session-scoped episodic records, read through `memoryEpisodicRecords`.
- **Namespaces** — records are namespaced by strategy and agent; prefixes such as `semantic_`, `preferences_`, and `episodes_` identify the extraction strategy.

`memorySystemConfig` reports the active engine and namespace configuration. AgentCore managed memory is the only engine.

## Known Limits

- **Extraction is not ours.** ThinkWork cannot force a fact into memory; it can only hand AgentCore the turn.
- **Wiki projection is separate.** Wiki pages are compiled context, not an upstream source of truth for retained memory.
- **Search is semantic-only.** It can miss exact IDs or unusual strings.
- **No bulk edit or bulk delete.** Every mutation is one record at a time.
