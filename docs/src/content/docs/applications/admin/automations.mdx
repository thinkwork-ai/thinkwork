An Automation is a **trigger** (schedule or webhook) bound to a **target** (agent
thread, routine, or workflow), optionally running as a user and optionally in a
Space. Manual "Run now" is an action on every Automation, not a configured
trigger. Schedule plumbing (`scheduled_jobs`, AWS Scheduler, EventBridge) and the
webhook substrate sit behind the product surface.

Active multi-step work appears in **Settings → Workflows**. Step Functions-backed
workflows still use the Routine adapter internally, so old Routine deep links
continue to resolve, but Routines are not a separate top-level product surface —
they show up as a target type on an Automation and as a Workflow row.

## Where it lives in the admin sidebar

```
Settings
├── Automations            ← /settings/automations
└── Workflows              ← /settings/workflows
```

There is **no separate Webhooks entry**. Webhooks are a trigger configuration of
an Automation; the endpoint URL and token are minted and shown inline on the
Automation. The previous `/settings/webhooks` page was retired once
webhook-trigger Automations shipped, and its delivery history now renders on the
owning Automation's detail.

## Automations

**Inventory route:** `/settings/automations`
**Detail route:** `/settings/agent-loops/:agentLoopId`
**Run-detail route:** `/settings/agent-loops/:agentLoopId/runs/:runId`

The inventory follows the Work Items list conventions — token filters and a
collapsed search. Columns are **Name, Trigger, Target, Status, Last run**.

Use an Automation when work should fire on a **schedule** or in response to a
**webhook**, and the thing to run is an agent thread, a routine, or a workflow.

### Creating an Automation

The New/Edit form is a single compact dialog showing exactly the model fields —
no Advanced accordion of runtime machinery, no preset sheet, no builder-thread
questions card:

1. **Trigger** — Schedule or Webhook. Schedule shows cadence controls (steered
   toward `cron()`); Webhook mints the endpoint URL + token inline.
2. **Target** — Agent thread, Routine, or Workflow. The form shows only that
   target's config: agent instructions for a thread target, a routine picker for
   a routine target, a workflow picker for a workflow target.
3. **Agent Instructions** (agent-thread targets only) — the labeled instruction
   field.
4. **Run-as user** — defaults to the creator; injected into the run's context.
5. **Space** — optional for routine/workflow targets (absent ⇒ headless);
   required for agent-thread targets.

A name is required but can be derived from the target config. Creation needs
exactly a name, a trigger, and a target.

### Spaces and headless runs

- **Agent-thread targets require a Space** — the run's conversation lives there.
  Save-time validation rejects a headless agent-thread automation with an
  actionable error.
- **Routine and workflow targets** may omit the Space. A run with no Space is
  **headless**: no thread is created on any dispatch path. This is how an
  Automation runs "outside a Space" without generating messages.

### Run-as context

Every Automation carries `run_as_user_id` (default: creator). Dispatch injects
that user's context per the Per-Sender Context Injection rule, entering through a
narrow service path with a tenant-membership cross-check — never by widening
`resolveCaller`.

### Webhook triggers

Webhook-trigger Automations reuse the existing webhook substrate (token auth,
idempotency, delivery audit) bound to the Automation. An inbound POST dispatches
through the same shared dispatcher as schedule and manual runs, with trigger
family `webhook`. Payload mapping v1 is raw JSON:

- routine/workflow targets receive the body as run input;
- agent-thread targets get the body appended to instruction context, wrapped in
  an explicit **untrusted-data fence** so the model never treats payload content
  as operator directives.

Delivery bodies can carry PII, so delivery history renders on the Automation
detail only where viewer permissions are equivalent to (not broader than) the
retired operator-only Webhooks page; otherwise body previews are redacted.

### Failure surfacing

- **Thread-target failures** surface in the execution thread.
- **Headless failures** raise a **deduplicated Inbox item** — one per failing
  automation, failure count incremented on retry. No silent failures.

## Workflows

**Inventory route:** `/settings/workflows`
**Detail route:** `/settings/workflows/:workflowId`
**Run-detail route:** `/settings/workflows/:workflowId/runs/:runId`

A Step Functions-backed workflow is an Amazon States Language state machine the chat builder agent emits, validated and provisioned by the Routine adapter's `publishRoutineVersion` GraphQL mutation. Each one has:

- **An ASL state machine** versioned via Step Functions `PublishStateMachineVersion`. The adapter records the version ARN so Workflow runs can show exactly which definition executed.
- **An agent-authored markdown summary** (`documentationMd`), regenerated on every publish, that names the steps the operator will see in the run-detail graph plus any HITL approval points.
- **A step manifest** (`step_manifest_json` on `routine_asl_versions`) that maps ASL state names to v0 recipe ids — the run-detail graph derives nodes from this manifest so brand-new executions render their shape immediately.
- **A visibility model** — `visibility = 'agent_private'` (only the owning agent can invoke) or `visibility = 'tenant_shared'` (any agent in the tenant). Splits the conflated `agentId` field; `owning_agent_id` is the authoring/stewardship agent for private Step Functions-backed workflows.

### The workflow inventory

The inventory aggregates Step Functions-backed workflows, n8n-connected workflows, CRM lifecycle workflows, and future connected-app/native sources. Columns show workflow identity, readiness, source, trigger family, lifecycle status, version, and last run. Blocked workflows remain visible with readiness reasons so operators can see missing OAuth, MCP, plugin, or engine prerequisites.

Step Functions-backed rows expose a Step Functions tab in detail, reusing the existing graph and definition panel. Source-specific setup remains on source pages such as `/settings/plugins/n8n`.

### The workflow detail page

Workflow detail has source-appropriate tabs:

- **Overview** — lifecycle, readiness, trigger family, source binding, and readiness reasons.
- **Step Functions** — only for `step_functions_routine` bindings; embeds the Routine adapter definition panel.
- **Runs** — recent Workflow runs with canonical status, trigger source, start time, and duration.
- **Definition** — version, source kind, capability snapshot, and definition snapshot.

### The workflow run-detail page

The customer-visible "watch the workflow execute" surface combines canonical Workflow ledger data with source-specific evidence:

- **`ExecutionGraph`** — vertical-stepper visualization of the state machine. Nodes derive from the routine_asl_versions step manifest backing this specific execution (resolved via `RoutineExecution.aslVersion`); fall back to deriving from `routine_step_events` when the manifest isn't fetchable. Latest-event-per-node selection collapses retry chatter into a single graph dot. Status icons: spinning loader for running, green check for succeeded, red X for failed, purple pause for awaiting_approval, amber clock for timed_out.
- **`StepDetailPanel`** — click a step in the graph; this panel shows input/output JSON, recipe type, retry count, LLM cost, duration. For `python` recipe steps with S3-offloaded stdout/stderr, the inline 4KB preview surfaces with a "(truncated)" marker plus the S3 URI for full output.
- **Workflow evidence** — backend/app proof such as Step Functions executions, n8n execution IDs, CRM event references, and redacted payload summaries.

The page polls every 5s while non-terminal. Subscription wiring (AppSync `OnRoutineExecutionUpdated`) is a follow-up — current polling is fine at current scale.

## Scheduled-Job Compatibility

**Compatibility detail:** `/settings/automations/:scheduledJobId`

The `scheduled_jobs` substrate behavior is unchanged. It still carries internal
scheduled work for evals, skill runs, idle-memory learning, Automation schedules,
and Workflow triggers. The EventBridge → `job-schedule-manager` → `job-trigger`
provisioning chain remains the operational wake path.

Operators should start by inspecting the owning product run:

- Automation schedule fired? Open the Automation run (thread or Inbox item).
- Workflow schedule fired? Open the Workflow run detail.
- No product run exists? Then inspect `scheduled_jobs`, AWS Scheduler, and
  `job-trigger` logs.

## What does _not_ live here

- **Workspace HITL reviews** — system-agent workspace reviews surface in [Inbox](/applications/admin/inbox/), not Automations or schedule plumbing. Workflow-driven HITL approvals (the `inbox_approval` recipe) also surface in Inbox; deciding an inbox item with `type = 'routine_approval'` resumes the paused Step Functions execution.
- **Per-thread agent invocations** — those live in [Threads](/applications/admin/threads/). Multi-step workflows are distinct: a Workflow run has its own ledger and, for Step Functions-backed workflows, adapter evidence in `routine_executions` rather than a `thread_turns` row.
- **Per-user OAuth or integration credentials** — those live in the mobile app. Admin owns tenant-wide infra and config; users own their own integration auth on mobile.
- **Legacy Python routines** — `engine = 'legacy_python'` rows are archived during the compatibility migration and excluded from active Workflow inventory. They're not deleted (status flips to `archived`); they stop being actionable from this UI.

## Under the hood

- **Automations:** `agent_loops` (name, description, enabled, `run_as_user_id`, optional `space_id`, primary trigger family) and `agent_loop_versions` — where `target_spec` (JSONB) is the **single authoritative version spec** describing the trigger and target. The old `goal_spec`, `worker_spec`, `loop_policy` columns and the judgment/evidence/ROI tables were dropped; `target_spec` is now dispatch-self-sufficient (THINK-137 / THINK-159).
- **Runs:** `agent_loop_runs` records each run with status, trigger family, and trigger source (`manual_run` for "Run now"). One shared dispatch ledger serves schedule, manual, and webhook paths, with recoverable idempotency and distinct side-effect sets for spaced (thread) vs headless runs.
- **Webhooks:** the `webhooks` substrate (token auth, idempotency, delivery audit) is now bound to an Automation rather than a standalone settings entity; the `webhooks` handler authenticates the public endpoint and dispatches through the shared automation dispatcher.
- **Workflows:** first-class `workflows`, `workflow_versions`, `workflow_triggers`, `workflow_engine_bindings`, `workflow_runs`, `workflow_run_events`, and `workflow_evidence` rows form the product control plane and run ledger.
- **Step Functions adapter:** `routines` stores the adapter record; `routine_asl_versions` is the ASL version history; `routine_executions` records each SFN execution; `routine_step_events` is the per-step event log. EventBridge bridges SFN execution-state-change events into `routine-execution-callback` so the adapter execution row tracks lifecycle even for `agent_invoke`-only workflows that have no wrapper Lambda.
- **Schedules:** `scheduled_jobs` table; `job-schedule-manager` reconciles to AWS Scheduler; `job-trigger` fires the owning Automation, Workflow, eval, skill, idle-memory, or other internal target.

`rate()` schedules treat the cadence as creation-time + interval, not wall-clock-aligned — a `rate(1 hour)` job created at 09:23 fires at 10:23, 11:23, … rather than on the hour. Use `cron()` for wall-clock alignment. The Schedule create form steers operators toward `cron()` for this reason.

User-initiated create and update Lambda invokes use `RequestResponse` so errors surface synchronously — no fire-and-forget paths.

## Rollout Notes

- Apply the Automation database migrations before deploying API/web code that expects the backing tables, including `agent_loops.space_id` and `agent_loops.run_as_user_id`.
- Destructive schema changes (dropping `goal_spec`/`worker_spec`/`loop_policy` or the judgment/evidence tables) follow expand/contract: ship the Drizzle definition-removal deploy first, then apply the drop migration. See `docs/solutions/workflow-issues/dropping-orm-declared-columns-needs-def-removal-deploy-first.md`.
- Keep `/api/scheduled-jobs` and `/api/job-schedules` routes deployed; internal jobs and compatibility details still use them.
- Do not introduce new REST routes for Automations unless GraphQL is insufficient.
