Artifacts are durable, named outputs agents produce during a turn — the deliverable, not the conversation about it. The Artifacts page is the tenant-wide gallery for browsing them; the artifact detail page is the full render with version history. For the underlying model (born-as-artifact, dual bodies, plates, bindings, the trust tiers), see [Concepts: Artifacts](/concepts/artifacts/).

**Routes:** `/artifacts` (list) · `/artifacts/<id>` (detail)

## Artifact types

`Artifact.type` is an **open string**, not an enum — plugins can mint their own kinds, and the UI renders every kind with a type badge. The types you will commonly see:

| Type                                  | Produced by                                                          |
| ------------------------------------- | -------------------------------------------------------------------- |
| `DATA_VIEW`                           | Living Canvases — GenUI widgets with data bindings                    |
| `REPORT`, `PLAN`, `BRIEF`, `IDEATION` | Document Artifacts — dual-body (markdown digest + plate-styled HTML) |
| plugin-defined kinds                  | Application plugins; rendered with the generic detail view            |

## The list view

A searchable table of every saved artifact in the tenant (drafts behind an "Include drafts" toggle): title with type badge, status, and freshness. Clicking a row navigates to the **full detail page** — there is no modal viewer.

## The detail page

- **Living Canvas** — chrome-free canvas render with muted header icons: **Refresh data** (when the canvas has bindings) and **Pin version**. Version history lists pinned versions with a read-only viewer.
- **Document Artifact** — the plate-styled HTML render in a sandboxed, scriptless frame, plus version history.
- **Other kinds** — generic metadata view with the raw content when renderable.

**Refresh just works:** tenant-scoped bindings refresh headlessly in seconds; a per-user connector binding refreshes under the clicking owner's own stored connection. Only a non-owner viewing someone else's per-user widget is asked to run the refresh through the agent. See [Concepts: Artifacts — Living Canvases and data refresh](/concepts/artifacts/#living-canvases-and-data-refresh).

## In threads

Every emission renders as prose plus a compact **artifact card** at the end of the agent's message (title, type badge, `Status · vN · freshness`). Clicking a card opens the artifact in a **docked, resizable panel** beside the thread; the panel updates live when chat edits re-emit the artifact. The thread header's panel button opens the newest artifact directly, or a picker when the thread produced several. The full page remains for deep links.

## How artifacts get created

Agents emit artifacts mid-turn (`emit_json_render_ui` for canvases, `emit_document` for documents). Both are **born as artifacts**: a draft row exists from first emission, and saving/finalizing flips status and pins versions. Emission is validated server-side — documents pass DocSpector (self-contained, scriptless, dual-theme, authored on the genre plate) or the agent is rejected in-turn and corrects itself.

The admin UI does not create or edit artifact content directly — artifacts are an agent-output primitive. Operators can save/pin canvases and finalize documents through the detail page actions.

## Known limits

- **No export button.** The document reader's print-to-PDF path is the export; there is no download-as-markdown affordance yet.
- **Sharing permalinks** (revocable public links to pinned versions) are planned, not shipped.
