Authored documents are the material where "what does the document say?" is the right question: a policy, a product FAQ, a runbook, an API reference. The **Reliability** operating guarantee lives here in a specific form — grounding the agent on a corpus you control means responses are reproducible against a known source, not synthesized from training-set memory the operator can't audit.

<Aside type="caution">
  **Brain Sources are retired.** The Space document-ingest path that retained
  authored documents into a per-Space memory bank was removed with the Hindsight
  memory engine. Bedrock AgentCore Memory holds extracted memory, not uploaded
  source corpora. Authored documents now reach agents as workspace files and
  compiled pages, described below.
</Aside>

## Where authored documents live now

- **Workspace files.** Drop the document into the agent, template, or tenant-default workspace. It is versioned in S3, mounted for the agent, and reachable through the workspace provider in Context Engine. This is the direct replacement for a small, curated authored corpus.
- **Compiled pages.** The [wiki compile pipeline](/concepts/knowledge/compounding-memory-pipeline/) distills what an agent has actually learned into entity, topic, and decision pages with per-section citations. This is the right home for knowledge that accumulates from work rather than arriving as a finished document.
- **Approved MCP tools.** When the canonical document already lives in a system with an API — a wiki, a ticket tracker, a docs site — an admin-approved MCP source is better than copying it. Context Engine loads it for the turn without making it durable memory.

## When to reach for authored documents

Document context is the right fit when:

- **The canonical answer lives in a document.** Product documentation, standard operating procedures, compliance policies.
- **You want citations.** Every retrieved hit should be traceable to a specific source file so agents can cite what they used.
- **The content changes occasionally, not continuously.** A runbook updated monthly is a good fit. A feed of live events is not.
- **You don't want the agent inventing facts.** Grounding reduces hallucination on questions where ground truth exists.

And it's the _wrong_ fit when:

- **The useful context is what this agent has learned across work** — that's [Retained Memory](/concepts/knowledge/memory/) and [compiled pages](/concepts/knowledge/compounding-memory/).
- **The content is massive and sparsely relevant** — a million-line codebase isn't an authored corpus; it's a search target for a different tool.
- **The question needs reasoning over a graph of entities** — document chunks won't reliably answer "which engineers owned which services in Q3."

## What happens at turn time

```
User message -> Context Engine queries workspace files + compiled pages -> ranked hits with citations -> model call
```

Concretely:

1. The document sits in a workspace scope the agent can see.
2. Context Engine's workspace provider matches it against the turn's query.
3. Hits return with provenance — source family, path, rank, freshness — and compete for the retrieved-context budget.
4. The model generates a response grounded in cited source content.

Nothing on this path writes durable memory. If a fact from a document should survive the thread, the agent retains it like any other fact and AgentCore extracts it.

## Known limits

- **No document-ingest surface.** There is no upload-and-retain flow; adding an authored source means adding a workspace file or approving an MCP source.
- **Retrieval is not graph-aware by itself.** Workspace search can't answer "which documents cite this one" — that's a graph question, better served by [compiled pages](/concepts/knowledge/compounding-memory/).
- **Scope is workspace scope.** A document is visible where its workspace is visible; there is no per-Space document bank.

## Under the hood

- **Storage.** Workspace files are versioned objects in the tenant S3 bucket, mounted into the runtime workspace.
- **Retrieval.** The workspace and wiki providers inside Context Engine; see the [Memory Context API](/api/context-engine/).
- **Code path.** ThinkWork-side orchestration lives under `packages/api/src/`; runtime workspace mounting lives in `packages/agentcore-pi/`.
