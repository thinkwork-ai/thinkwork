Memory is the context layer agents use before they act. It is not a single database, vector index, or chat-history trick. It is the ThinkWork-owned layer that decides what an agent should know for the current turn, where each fact came from, how fresh it is, and whether it is durable enough to carry forward.

The clean model is:

- **Threads** keep the complete record of work.
- **Memory** assembles the context that should matter now.
- **Agents** reason and act using that assembled context.

That distinction matters. Threads answer "what happened?" Memory answers "what should the agent know before it responds or takes action?"

<Aside type="note">
  Some route paths and older implementation names still use `knowledge` or
  `brain` for compatibility. The visible component names in the docs are Memory
  and ThinkWork Brain.
</Aside>

## What It Contains

Memory is an umbrella over durable AgentCore memory plus source families that can be inspected or lazy-loaded. Operators see them together in Admin because they all affect what an agent can know, but each source keeps its own contract and provenance.

## Why It Exists

Most agent systems expose memory, RAG, workspace search, and external search as separate tools. That makes agents choose implementation details mid-turn and makes operators debug the wrong layer: was the answer bad because the memory engine missed, the source was stale, or the agent never called the right tool?

Memory puts those sources behind one operator boundary:

- operators can inspect and test the sources together;
- agents can use durable memory plus external context without hard-coding every backend;
- every hit carries provenance, source family, rank, freshness, and provider status;
- backend choices can change without changing the product story.

## How a Turn Uses Memory

At turn time, the runtime combines recent thread history, AgentCore memory recall, compiled pages, workspace files, and approved external context tools. Context Engine ranks and budgets lazy-loaded external results before the model sees them.

```
User message arrives in a thread
        │
        ▼
  Turn context assembly
        │
        ├─ Recent thread history
        ├─ AgentCore memory recall
        ├─ Compiled pages
        ├─ Workspace files
        └─ Approved MCP search tools
        │
        ▼
  Assembled context → model/runtime
        │
        ▼
  Response + tool calls → thread
```

Every external source is optional. A focused support bot may only need its Space workspace files. A long-running sales agent may use retained memory, compiled customer pages, workspace files, and approved operational search tools.

## Trust and Provenance

Memory treats source trust as a product concern, not a prompt afterthought.

- **Authored knowledge** comes from workspace files and keeps path/version citations.
- **Memory** comes from prior work and keeps namespace and record references.
- **Compiled pages** summarize many source facts and keep page-section provenance.
- **External MCP hits** are transient unless a separate workflow promotes them.
- **Operational facets** can be live and fresh, but should not be silently converted into durable narrative facts.
- **Company Brain knowledge collections** (SOPs, manuals, policy documents,
  reached through the Brain's knowledge connector) return passages with
  their source documents. Agent answers built from them carry **inline
  citation pills** and a **"Used N sources"** panel; clicking a source
  opens the actual document — Office formats in the in-app viewer, at the
  cited page when the passage carries one.

<Aside type="note">
  Conversation-transcript collections (the hourly thread sweep) are
  excluded from broad knowledge searches so document answers never cite a
  past conversation as a "source". Transcripts stay fully searchable when
  the agent — or a scoped bundle — names that collection explicitly.
</Aside>

<Aside type="note">
  The internal Context Engine service and `query_context` tool are still the
  developer contract behind Memory source routing. Product-facing docs use
  Memory; API reference docs still name the exact contract developers call for
  external context.
</Aside>

## Admin Surface

In Admin, the operator Memory surface lives at `/settings/memory`:

| View            | Purpose                                                                        |
| --------------- | ------------------------------------------------------------------------------ |
| Memory          | Browse, search, and edit operator-visible AgentCore memory records             |
| Wiki            | Inspect compiled pages and page search output                                 |

Older paths and implementation names may still use `knowledge` for
compatibility, but the canonical operator route for this pass is
`/settings/memory`.
