Eval Execution Tiers

Requirements — phase 2 of the Evaluation Framework (THINK-107)
type feat date 2026-07-02 readiness requirements-only contract ce-unified-plan/v1 authority Eric Odom
Objective. Make evaluation volume scale by matching each test case to the cheapest execution that can honestly answer it — a unit / component / integration tier split — so “thousands of evals against multiple profiles” stops meaning thousands of full agent turns.

Trigger: the 2026-07-02 dev benchmarks. Even after the throughput fixes (#3191, #3195), a 189-case full-agent baseline run costs ~23 min and ~$1.20 per profile, bounded by Bedrock quota. Workable for one baseline — not for thousands.

The judge isn't the problem — evaluator cost is a small fraction. The problem is that every case pays for a full AgentCore turn (workspace bootstrap, skill materialization, MCP wiring, memory plumbing) whether or not the behavior under test needs any of it.

The tier model

Tier 0 · unit

static

Score an already-recorded output. Flagged-thread snapshots; regression re-scoring after rubric edits. Zero model invokes on the response side.
~ms · ~$0 · no Bedrock dependency
Tier 1 · component

model

One stateless Converse call — profile's model + composed prompt + case query. No workspace, no tools, no MCP, no memory. Batched N-per-worker: “a single agent running a bunch of tests.” Fits most refusal-shaped baseline cases.
~1–2s · ~$0.001–2/case · batched
Tier 2 · integration

agent

Today's full Pi turn via AgentCore. Required when behavior depends on tools, skills, workspace state, MCP boundaries, or multi-message replay. Skill evals and thread replays stay here.
~7.5s · ~$0.006/case · ground truth

Scoring is orthogonal and unchanged: deterministic assertions always run; llm-rubric judges run per the case; trials/unstable apply regardless of tier. Profiles, pinning, telemetry, comparisons — all phase-1 substrate carries over untouched.

Requirements

R1
Case schema (seed packs, dataset files, Studio) gains execution_tier: static | model | agent. Missing = agent — nothing silently gets cheaper.
R2
The runner fans out by tier: tier-2 keeps per-case messages; tier-1 batches N-per-message into the same FIFO/profile machinery; tier-0 scores inline or in one batch.
R3
Tier-1 uses the pinned profile's model and records identical per-case telemetry (tokens, cost, duration) — the comparison view stays honest with no changes.
R4
One-time classification pass over the 189 baseline cases → adjudication PR (same channel as the quality_state audit). Expected: ~80% tier-1, ~20% tier-2.
R5
Tier is visible: result rows carry the executed tier; run detail badges it; cross-tier comparisons flag non-comparable (extends the KTD6 gate).
R6
Honesty guard: cases asserting on tool calls, guard events, or workspace projections reject cheap tiers at authoring/adjudication — a tier-1 execution can't produce that evidence.
R7
Mixed-tier runs finalize correctly: expected-row accounting, trials, and the reconciler treat tier as an execution detail of a row, not a new lifecycle.

Acceptance examples

AE1 — Post-classification baseline run: tier-1 majority executes in minutes; run detail shows tier badges; pass-rate math unchanged.
AE2 — A case with a workspace-projection-* assertion cannot be saved as tier model; authoring surfaces the conflict.
AE3 — Comparing runs whose tier map changed between them renders a non-comparable flag, like dataset-version drift.
AE4 — A flagged-thread case re-scored as tier-0 after a rubric edit yields a new result row with zero agent cost and the recorded output as evidence.
AE5 — 4 profiles × baseline × trials 3 completes within an hour on dev at current quotas (vs ~9h today).

Success criteria

  1. Baseline per-profile wall clock: ~23 min → single digits, no quota change.
  2. Cost per baseline run drops ≥ 60%.
  3. Zero honesty regressions: no case scores under a tier that can't produce its required evidence; tier visible everywhere verdicts are.

Open questions — need Eric's call before planning

Q1 · Tier-1 system prompt. Case's own prompt, the tenant's composed agent prompt, or a neutral harness prompt?
▸ Recommend: composed prompt captured once per run (pinned like the profile snapshot) — representative behavior, one bootstrap per run instead of 189.
Q2 · Where does tier live? On the case (curated, adjudicated) vs on the run vs both.
▸ Recommend: on the case + a run-level “force full-agent” override — nightly runs tier-mixed and cheap, weekly all-agent audit catches drift the cheap tier misses.
Q3 · Batch failure isolation. N cases per tier-1 message — one case's throttle/timeout must not fail the batch (per-case try/catch, partial results written). What's the right N?
Q4 · Tier-0 storage. Likely none needed — flagged payloads already persist; the worker needs a “score this stored output” path, not new capture.
Handoff: on confirmation, ce-plan enriches this artifact in place to implementation-ready. Prior art: the ScoringEngine seam (packages/evals-core/src/engine.ts), runner batching, the quality_state adjudication channel, and the KTD6 comparability gate this extends.
